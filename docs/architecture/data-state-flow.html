00一句话概览

这个客户端没有后端服务，也没有使用 Room/SQLite。整份用户数据是一个 JSON 文档（library.json）， 内存里同时存在两份副本：界面层的一份（MainActivity.library）和后端工作副本 （JsonStoreBackend.workingCopy）。两者只在「提交」这一刻通过一份整文档快照对齐。

01 · 单一文档

全量快照，而非增量行

词汇、笔记、会话、复习计划全在同一个 JSON 里。每次写入都是「整份文档替换」，没有局部 UPDATE。

02 · 单线程串行

所有写排队执行

LibraryStore 只有一条名为 LexiNote-StoreWorker 的工作线程，FIFO 执行，天然无并发写。

03 · 世代屏障

恢复即换纪元

每次备份恢复或回退都把 generation 加一，在途的旧命令因世代不符被整条丢弃。

读图约定 实线箭头表示正常路径；虚线框表示已声明但当前未生效的分支； 绿 表示提交成功，黄 表示可恢复的拒绝， 红 表示数据未被写入的失败。

02写入主链路：一次保存的 11 步

绝大多数用户操作（新增词汇、改笔记名、记一次复习评分）都走同一条路：先在内存里改，再把整份文档提交。 下面以「点保存把查询结果存入笔记」为例，按真实调用顺序展开。

  1. QueryUi · 领域方法调用

    界面直接在 a.library 上调用 saveResult(...)。此刻只改内存，磁盘毫无变化。

  2. MainActivity.change(Runnable) · 保护壳

    先把当前文档 snapshot() 存进局部变量 before；一旦修改块抛异常，就用它把 library 整体换回去，界面立即恢复原状。

  3. MainActivity.persist() · 取快照

    library.snapshot() 做一次 JSON 深拷贝；同时把 committed 指向这份新快照（含义是「最后一次提交出去的版本」，不是「最后一次落盘成功」）。

  4. LibraryCommand.persistSnapshot(gen, snapshot, now)

    包装成类型为 MUTATE_CUSTOM 的不可变命令：payload 里装着整份 snapshot，同时携带 expectedGeneration、eventId、timestamp。payload 在构造时就已深拷贝，之后 UI 再改内存也不会影响这次提交。

  5. LibraryStore.dispatch(token, command, callback)

    把 Activity 当作生命周期令牌登记，然后把任务丢进唯一的 LexiNote-StoreWorker 线程队列。调用立即返回，主线程不阻塞。

  6. 调度层 · 世代闸门

    工作线程取出任务后先比对：expectedGen > 0 && expectedGen != backend.getGeneration() 就直接返回 GENERATION_CONFLICT，根本不进后端。这挡住的是「恢复备份期间排队等待的旧写入」。

  7. JsonStoreBackend.execute() · 二次校验 + 留底

    后端不信任上游，自己再校验一次世代，然后 beforeSnapshot = workingCopy.snapshot() 留一份事务前副本。整个方法是 synchronized 的，且只可能被工作线程调用。

  8. MUTATE_CUSTOM 分支 · 整文档替换

    workingCopy = new Library(payload.optJSONObject("snapshot"))。构造函数里会跑 validate() 并补齐系统笔记（nb_default、nb_global_root）、重建全局索引、规范会话元数据。

  9. Repository.save() · 原子写盘

    先 Library.validate() 校验整份文档，再序列化成 UTF-8 字节；超过 min(4 MB, 堆/32) 直接抛「笔记文本超过当前设备容量」。正常路径走 AtomicFile.startWrite / finishWrite；宿主 JVM 或 AtomicFile 不可用时回落到 .new → .bak 重命名方案。

  10. 提交成功 · revision + 1

    revision++，返回 SUCCESS，并把落盘后的新快照塞进 CommitResult 一起带回。

  11. 回调 · 回到主线程

    投递前检查令牌是否仍然绑定：Activity 已 unbind 就静默丢弃（防内存泄漏与陈旧 UI）。仍然绑定则执行 library = result.getSnapshot(); render();，界面以磁盘回读后的权威快照重绘。

为什么不直接写文件 第 2 步到第 5 步全在主线程完成，只有序列化与 IO 落到工作线程。主线程因此不会因为几 MB 的 JSON 卡住； 代价是「提交」与「落盘」之间有窗口期，见 风险清单 第 1 条。

03读取链路：内存优先，查询兜底

读有两条完全不同的路径，理解它们的差别是理解整个状态模型的关键。

路径 A · 主路径

直接读内存副本

render() 完全基于 MainActivity.library 这个可变对象构建视图。 没有等待、没有回调、没有失败分支。这也是为什么界面代码可以写成同步风格。

代价：读到的可能是「已提交但尚未落盘」的状态，也可能与后端 workingCopy 短暂不一致。

路径 B · 预留路径

结构化查询 ReadOnlyView

store.query(request, cb) 进入同一条工作线程队列，因此必然看到此前所有已完成的写。 返回的 ReadOnlyView 每个 getter 都做深拷贝，UI 拿到的是隔离快照。

现状：界面尚未使用它；PLAN_STATISTICS 与 SESSIONS 会落到 default 分支返回整份快照。

查询类型与真实行为

设计意图 StoreBackend 是一个 SPI。当前的 JsonStoreBackend 只是过渡实现——注释里写明未来会换成 SqliteLibraryStore 做增量事务。正因为查询走的是这套接口，界面层不需要为「整文档」和「按行查」的差异做任何改动。

声明在契约里的是八种。实际代码会产出的只有六种，剩下两种是接口预留。

同步路径（change() 内部抛异常）会回滚 UI 内存；但第 11 步的异步失败只触发 error(new IOException("后台写入失败：" + …))，不会把 library 换回 committed。

一致性缺口 一次后台写入失败后，后端持有的是旧文档，界面持有的是新文档。直到下一次成功提交（整文档替换）才会重新对齐； 在此之前任何基于界面的读取都会显示「未落盘的内容」。

05并发控制：四道闸门

这套模型没有锁竞争，靠的是「串行 + 版本 + 令牌 + 请求代号」四层防护。

闸门 1

单线程队列

Executors.newSingleThreadExecutor，线程名 LexiNote-StoreWorker。 提交按 FIFO 顺序执行，execute() 与 applyTransaction() 都只在它上面跑。

推论：读查询排在同一队列里，所以「先写后读」一定看得见写入结果。

闸门 2

世代屏障 generation

初值 1。仅在 restore()、rollback()、迁移时自增。 命令携带 expectedGeneration，不符即丢弃；传 0 表示主动跳过检查。

实现在调度层与后端层各有一份，形成双重校验。

闸门 3

版本 revision

每次成功提交 + 1；幂等忽略不加；恢复与回退后归零。 它把「同一世代内的第几次提交」变成可比较的数字，供界面判断结果是否过期。

TitleSuggestionGuard 要求五个条件同时成立才采纳异步标题：会话仍存在、未被手动命名、 revision 未变、epoch 未变、当前标题仍为空。

闸门 4

生命周期令牌 token

onCreate 里 bind(this)，onDestroy 里 unbind(this)。 令牌集合用 WeakHashMap 支撑，解绑后的回调在投递前被拦下。

旋转屏幕销毁重建时，属于旧 Activity 的回调不会打到新实例上。

界面层还有一层「请求代号」

网络请求与存储提交是两件事，界面另有一套逻辑防止迟到的回复覆盖新状态：

06启动与损坏恢复：三条分支

应用启动时先决定「这次能正常用，还是只能进恢复模式」。

分支 A · 正常

读取成功。Activity 通过 getWorkingLibrarySnapshot() 拿到一份深拷贝作为界面副本，同时把 committed 指向同一份内容。

分支 B · 首次启动

文件与 .bak 都不存在时返回一个空 Library：写入 version、四个空数组、空 settings， 并自动补出两个系统笔记。

分支 C · 读取失败

解析异常被记录到 initError 并向外抛。Activity 捕获后置 recoveryOnly = true， 只渲染一个「恢复本地数据」页。

恢复模式下发生了什么 界面不加载任何业务页面，persist() 直接返回 false——此时不可能覆盖损坏的文件。 用户选择备份后，先 repository.preserveCorruptData() 把原始字节另存为 library-corrupt-<时间戳>.json，再执行恢复。

为什么能容忍半截文件

三层保险叠在一起：AtomicFile 用「写临时文件 → fsync → rename」保证替换原子性； 宿主 JVM 回落路径额外保留 .bak；Repository.load() 发现主文件读不出来时会尝试把 .bak 提升回主文件。任一层成功，用户就看到完整文档而不是半截 JSON。

重启后会丢什么：第三类状态

并非所有状态都进 library.json。界面自身的状态既不在文档里，也不进快照， 只靠 onSaveInstanceState 撑过一次配置变更（如旋转屏幕）。

状态存放处能活多久

07备份、恢复与回退：世代如何跃迁

这是唯一会改变 generation 的用户操作，也是整个模型里最值得单独画图的一段。

导出

导出过程只读不写，不改变 generation/revision；API Key 在另一个存储域，因此天然不在归档里。

恢复（含失败兜底）

  1. 选择文件 → 后台解析

    校验 CRC32、拒绝异常路径、限制图片数量（≤1998）与总字节；文本超过 4 MB 直接拒绝，已有数据保持不动。

  2. 确认覆盖 → materialize 图片

    把归档里的图片逐个写到 files/restored/<uuid>/，并把 JSON 里的引用改写成本机 file:// 地址。

  3. Repository.restore(backup, current)

    先把当前文档写进 before-restore.json，再 save() 新文档。这一步是「回退」能成立的全部前提。

  4. 替换界面内存 + 清空易失状态

    library = restored，同时清掉 session、图片编辑态、复习队列、笔记选中项与标题缓存，再整体重绘。

  5. dispatch(importLibrary(0L, backup))

    后端也执行一次 restore()：记住 preRestoreBackup，换上新文档，generation + 1，revision = 0。传 0L 表示故意跳过世代检查。

世代跃迁的意义 假设恢复开始时队列里还躺着一条旧写入（拿着 gen=1）。恢复把它推到 gen=2 之后，那条命令的 expectedGeneration 就对不上了，被 GENERATION_CONFLICT 拦下—— 旧数据不会在恢复完成后偷偷覆盖新数据。

08会话数据生命周期：三种留存等级

会话是唯一有「自动淘汰」规则的数据类型。淘汰不是定时任务，而是每次写入会话时顺手重算： touchSession() 末尾会重建整个 conversations 数组。

query查词会话 · 只在最近 10 条内保留
进入 AI 对话
temporary临时会话 · 最多 5 条
用户点保存
saved永久 · 不受任何上限约束
保留公式

保留 = saved ∪（按 last_used_at 倒序的前 5 条 temporary）∪（id 出现在 recent_queries 里的 query）。其余全部丢弃。

最近查询

recent_queries 按 created_at 倒序裁到 10 条。 删除一条最近查询会立刻触发 pruneQuerySessions()，把失去索引的 query 会话一并清掉。

升级不可逆

promoteTemporary() 会把非 saved 会话标成 temporary 并打上 ai_session_entered；saved 一旦成立，后续调用直接返回，不会降级。

为什么空会话不挤占名额 打开一个空白助手输入框时，代码只把 metadata.origin 改成 assistant， 不调用 promoteTemporary。这样「点一下助手再退出」不会淘汰掉正在用的临时会话—— 这正是 2026-10-28 那轮使用体验审查里修掉的问题之一。

12不变量与风险清单

以下六条都能在代码里指出具体位置，按影响面排序。

  • 提交成功 ≠ 落盘成功（异步窗口）。 persist() 在 committed = snapshot 之后才异步派发，而 committed 的语义是「最后提交出去的版本」。如果此时进程被杀，界面曾显示过的内容可能并未写入磁盘。
  • 异步失败后两端内存不一致。 JsonStoreBackend 会把 workingCopy 回滚到 beforeSnapshot， 但 MainActivity.library 仍是新快照，只弹了一个错误框。要等下一次成功提交才会重新对齐。
  • 恢复路径绕过了单线程队列。 MainActivity.restore() 先在主线程侧直接调用 repository.restore() 写盘， 随后才向 store 派发 importLibrary(0L, …)。同时传 0L 主动跳过世代检查—— 若此刻队列里还有在途写入，理论上存在覆盖窗口。
  • 整文档写入的代价随数据量线性增长。 每次提交都要 snapshot() 深拷贝、validate() 全量校验、序列化整份 JSON 再原子替换。 1000/3000 条量级的验收里已经观察到评分约 1.1 秒与滚动掉帧，与这条路径直接相关。
  • 两个状态字段的实际产出少于声明。 ENTITY_NOT_FOUND 与 DISPOSED 从未被构造：实体缺失统一表现为 VALIDATION_FAILED，令牌失效则直接不投递回调。调用方若按枚举穷举处理会多出死分支。
  • 查询接口尚未真正用起来。 PLAN_STATISTICS 与 SESSIONS 会落到 default 返回整份快照， 界面也仍以内存直读为主。这套 SPI 目前更像为未来 SQLite 迁移预留的接口，而不是当下的性能手段。

一句话记住这个模型

界面改的是自己那份 JSON，提交时把整份文档交给唯一一条工作线程， 线程用世代号判断这份提交是不是已经过期，过期就丢、合法就整份替换并原子写盘； 写完把权威快照丢回主线程，界面照着重画。
